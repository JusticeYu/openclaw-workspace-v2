# 季度立项管理技能

本技能协助完成完整的季度立项流程，从特性优先级排序到立项评审材料准备。

## 适用场景

1. **特性优先级排序** - 对候选特性进行优先级评估和排序
2. **圈定季度特性** - 根据资源情况确定本季度立项的特性范围
3. **生成规划报告** - 输出PPT格式的特性规划报告
4. **用户故事拆分** - 协助拆分用户故事并评估人天
5. **维护成员系数** - 管理项目组成员的投入系数
6. **计算工作日** - 计算季度工作日（扣除节假日、周末、补班）
7. **评估负荷** - 计算项目组负荷情况
8. **立项评审准备** - 准备评审所需材料

## 立项流程

### 阶段一：特性准备

1. **收集候选特性**
   - 从金蝶系统导出候选特性清单
   - 确认特性基本信息（名称、描述、业务价值）

2. **特性优先级排序**
   - 使用优先级矩阵（业务价值 vs 实现成本）
   - 建议采用 MoSCoW 方法：
     - Must have：必须在本季度完成
     - Should have：应该完成，有一定灵活性
     - Could have：可以完成，资源允许时纳入
     - Won't have：明确排除，放入 backlog

### 阶段二：资源评估

1. **计算季度工作日**
   ```
   季度工作日 = 自然工作日 - 节假日 - 周末 + 补班日
   ```
   - 使用 scripts/workday_calculator.py 计算
   - 参考 references/holidays_YYYY.md 中的节假日数据

2. **维护成员系数**
   - 在项目系数表中维护每个成员的投入系数
   - 系数范围：0.0 - 1.0（1.0 = 全职投入）
   - 区分角色：开发、测试、产品
   - 示例：
     ```
     张三（开发）：0.8（80%投入本项目）
     李四（测试）：1.0（全职）
     王五（产品）：0.5（50%投入）
     ```

3. **计算项目组负荷**
   ```
   负荷率 = 实际立项故事总计划人天 / (系数总和 × 季度工作日)
   
   其中：
   - 系数总和 = Σ(开发系数) + Σ(测试系数) + Σ(产品系数)
   - 建议负荷率范围：70%-85%
   ```
   - 使用 scripts/capacity_calculator.py 计算

### 阶段三：用户故事拆分

1. **故事拆分原则**
   - 每个故事应可独立交付价值
   - 故事粒度：通常 1-5 人天
   - 遵循 INVEST 原则：
     - Independent（独立的）
     - Negotiable（可协商的）
     - Valuable（有价值的）
     - Estimable（可估算的）
     - Small（小的）
     - Testable（可测试的）

2. **人天评估**
   - 与SM一起评估每个故事
   - 分别评估：开发人天、测试人天、需求人天
   - 使用规划扑克或亲和估算方法
   - 记录到金蝶系统中

### 阶段四：规划报告

1. **生成PPT报告**
   - 使用 assets/planning_template.pptx 模板
   - 填充以下内容：
     - 季度目标概述
     - 立项特性清单（含优先级）
     - 资源分配情况
     - 负荷评估结果
     - 风险与依赖
     - 里程碑计划

2. **报告结构**
   - 封面：项目名称、季度、日期
   - 目录
   - 季度目标与策略
   - 特性规划（按优先级排序）
   - 资源与负荷分析
   - 里程碑与关键节点
   - 风险与应对措施
   - 附录：详细故事列表

### 阶段五：立项评审

1. **评审材料准备**
   - 规划报告PPT
   - 特性详细说明
   - 用户故事清单
   - 人天评估明细
   - 负荷计算表

2. **评审要点**
   - 特性优先级是否合理
   - 资源分配是否充足
   - 负荷率是否在合理范围
   - 风险是否识别充分
   - 依赖关系是否明确

## 工具脚本使用

### 计算季度工作日

```bash
python scripts/workday_calculator.py --year 2026 --quarter 2
```

参数：
- `--year`：年份
- `--quarter`：季度（1-4）

输出示例：
```
2026年第二季度工作日计算：
- 起始日期：2026-04-01
- 结束日期：2026-06-30
- 总天数：91天
- 周末：26天
- 节假日：3天（清明1天、劳动节1天、端午1天）
- 补班：0天
- 工作日：62天
```

### 计算项目组负荷

```bash
python scripts/capacity_calculator.py \
  --workdays 62 \
  --dev-capacity 2.8 \
  --test-capacity 1.5 \
  --product-capacity 0.8 \
  --total-days 180
```

参数：
- `--workdays`：季度工作日
- `--dev-capacity`：开发系数总和
- `--test-capacity`：测试系数总和
- `--product-capacity`：产品系数总和
- `--total-days`：立项故事总计划人天

输出示例：
```
项目组负荷评估：
- 季度工作日：62天
- 开发系数：2.8
- 测试系数：1.5
- 产品系数：0.8
- 系数总和：5.1
- 总可用产能：316.2 人天
- 计划人天：180 人天
- 负荷率：56.9% ✅ （建议范围：70%-85%）
- 剩余产能：136.2 人天
```

## 数据管理

### 金蝶系统数据

目前数据在金蝶苍穹系统中维护：
- 特性清单
- 用户故事
- 人天评估
- 成员系数

**暂时无API对接**，需要手工导出/导入数据。

### 本地数据文件

建议在本机维护以下文件（Excel/CSV格式）：

1. **特性清单表** `features_QX_YYYY.xlsx`
   - 特性ID、名称、描述、优先级、状态

2. **用户故事表** `stories_QX_YYYY.xlsx`
   - 故事ID、所属特性、描述、开发人天、测试人天、需求人天

3. **成员系数表** `capacity_QX_YYYY.xlsx`
   - 姓名、角色、系数

4. **负荷计算表** `load_calculation_QX_YYYY.xlsx`
   - 自动计算负荷率

## 最佳实践

1. **提前规划**：在季度结束前2周开始准备
2. **数据备份**：定期导出金蝶数据到本地备份
3. **系数调整**：根据实际情况动态调整成员系数
4. **负荷缓冲**：保留20%缓冲，应对突发需求
5. **定期同步**：与SM每周同步故事拆分进度
6. **风险前置**：在规划阶段识别并沟通风险

## 季度RP（Release Planning）检查清单

本检查清单用于规范软件研发项目的立项和规划过程，分为四个层级：**检查项 → 明细项 → 检查点 → 自检负责人**。

### 角色说明
- **PO（Product Owner，产品负责人）**：负责特性相关的规划和文档检查
- **SM（Scrum Master，敏捷教练）**：负责用户故事、资源维护和负荷检查

---

### 一、特性列表规范度（自检负责人：PO）

| 检查项 | 明细项 | 检查点 | 备注 |
|--------|--------|--------|------|
| 特性状态标记 | 特性状态准确性 | 状态必须正确，至少要规划完成 | 🔴 红色警示：无法立项 |
| 特性发布计划 | Release字段设置 | Release字段设置必须正确 |  |
| 发布完整性 | 特性发布完整性 | 确认特性在Release中一次性发布完成，不能拆分 |  |
| P0级特性规划 | 规划报告输出 | P0级特性需输出规划报告并评审通过 |  |
| P0级特性设计 | 设计报告识别 | 立项时只需识别勾选，迭代过程中输出报告 | 🔴 红色警示 |

---

### 二、特性规划文档（自检负责人：PO）

| 检查项 | 明细项 | 检查点 | 备注 |
|--------|--------|--------|------|
| 文档归档 | 规划文档准备 | 特性列表中标识需要规划文档的特性，需准备PPT/WORD格式 |  |
| 文档存储 | 文档归档位置 | 放入VSS（版本控制系统）对应目录 |  |

---

### 三、用户故事列表（自检负责人：SM）

| 检查项 | 明细项 | 检查点 | 备注 |
|--------|--------|--------|------|
| 缺陷转需求立项 | 非功能需求覆盖 | 缺陷转用户故事的需求（包含性能、安全等非功能需求）必须进行立项 |  |
| 迭代阶段范围 | 时间范围合规 | 必须在当前季度Release范围内 | 示例：4月迭代一~6月迭代二 |
| 迭代目标 | 目标状态设置 | 目标状态为"发布完成" |  |
| 工作量评估 | 故事粒度控制 | 80%的用户故事估算 ≤ 10人天 | 针对立项的用户故事完成工作量评估 |

---

### 四、资源维护（自检负责人：SM）

| 检查项 | 明细项 | 检查点 | 备注 |
|--------|--------|--------|------|
| 资源维护完成度 | DMP项目组资源 | 项目组资源维护必须完成 |  |

---

### 五、资源负荷（自检负责人：SM）

| 检查项 | 明细项 | 检查点 | 备注 |
|--------|--------|--------|------|
| 负荷率标准 | 负荷率合规性 | 资源负荷需达到 90~100% | 涵盖领域总体、需求、开发、测试负荷，以及项目组整体负荷 |
| 负荷检查方式 | 看板验证 | 通过DMP项目看板进行检查验证 |  |

---

### 检查清单使用指南

1. **逐项检查**：按照检查清单逐项核对，确保所有检查点都已满足
2. **责任落实**：每个检查项有明确的自检负责人，PO和SM分工协作
3. **红色警示项**：标注🔴的检查项为关键项，未达标将导致立项失败
4. **记录证据**：对于文档类检查项，保留归档路径和文件名
5. **持续改进**：定期回顾检查清单，根据实际执行情况优化

## 常见问题

**Q：负荷率超过100%怎么办？**
A：需要调整立项范围，减少低优先级特性，或申请增加资源。

**Q：负荷率90-100%会不会太高？**
A：这是饱和管理的策略，确保资源充分利用。如果持续超过100%，需要评估资源瓶颈并优化。

**Q：P0级特性设计报告为什么要在迭代中输出？**
A：为了保持敏捷开发的灵活性，立项时先识别需要设计报告的P0级特性，在迭代过程中细化输出，避免过早过度设计。

**Q：用户故事粒度为什么要求80%≤10人天？**
A：10人天以内的故事粒度更容易跟踪、评估和调整，符合敏捷开发的小步快跑原则。

**Q：成员系数如何确定？**
A：根据成员在本项目的实际投入比例，考虑并行项目情况。

**Q：故事人天评估不准怎么办？**
A：采用相对估算，使用故事点而非绝对人天，或增加缓冲系数。

**Q：节假日数据需要更新吗？**
A：每年年底国务院发布下一年放假安排后更新 references/holidays_YYYY.md。

**Q：VSS是什么？**
A：VSS（Version Control System）是版本控制系统，用于文档归档和版本管理。
